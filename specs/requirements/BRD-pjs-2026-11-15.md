# Business Requirements: PJS (Priority JSON Streaming)

> [!abstract]
> PJS lets a server send a large JSON document as a skeleton plus prioritized patches so a client can render the important parts first. This BRD is reverse-engineered from the shipped product (README, `docs/architecture/SPECIFICATION.md`, CHANGELOG, code) and records the business intent behind the existing capability specs. It is a baseline for future work, not a new commitment.

> [!warning] Assumptions
> - Business goals below are inferred from README positioning and project history; maintainer confirmation is pending (see Open Questions).
> - Version reference: workspace 0.8.0.

## 1. Executive Summary

PJS (`pjson-rs`) is an open-source (MIT OR Apache-2.0) Rust library plus WebAssembly and TypeScript clients implementing a priority-based JSON streaming protocol. The same bytes are sent, only the order changes: layout and critical fields arrive first, heavy tails last, cutting perceived latency (design target 5-10x) on slow or unstable networks. It is positioned between plain REST/JSON and framework-bound solutions (React Server Components, GraphQL `@defer`/`@stream`).

## 2. Problem Statement

- A large JSON response is all-or-nothing: the client cannot render before the last byte arrives.
- Teams on plain REST stacks lack a framework-agnostic way to get progressive rendering without adopting GraphQL or RSC.
- Streaming parsers and decompressors on the server are a denial-of-service surface; naive implementations are unsafe by default.
- High-throughput JSON handling in Rust services demands SIMD parsing and low dispatch overhead.

## 3. Target Users

| Persona | Need | Primary surface |
|---------|------|-----------------|
| Backend developer (Rust) | Serve large JSON with priorities from an axum service | `pjson-rs` crate, HTTP/WebSocket adapters |
| Frontend developer (browser/Node) | Render partial data as frames arrive | `pjs-wasm` npm package, `pjs-js-client` |
| Platform / SRE | Operate the server safely: limits, auth, metrics, graceful shutdown | HTTP middleware, metrics, `serve_with_limits` |
| Security reviewer | Assurance that untrusted input and decompression are bounded | security subsystem, fuzz targets, advisories |
| Contributor / maintainer | Predictable architecture, CI and release flow | workspace, specs, CI |

## 4. Business Objectives

| ID | Objective | Success indicator |
|----|-----------|-------------------|
| BO-001 | Deliver a usable skeleton-plus-patches protocol over HTTP, SSE/NDJSON and WebSocket | End-to-end flow works in Rust server, browser WASM and Node |
| BO-002 | Make progressive rendering the cheap default for large payloads | Priority assignment and frame generation need no custom client parser |
| BO-003 | Be safe against hostile input by default | Default limits on size, depth, cardinality, decompression; fuzz targets in CI |
| BO-004 | Be demonstrably fast | SIMD parser selection at runtime; GAT ports measured 1.82x faster than `async_trait`; benchmarks in CI-adjacent workflow |
| BO-005 | Keep the wire format and public API honest while pre-1.0 | Breaking changes documented in CHANGELOG; wire format spec draft |
| BO-006 | Reach stable Rust support on the road to 1.0 | Open: currently nightly-only |
| BO-007 | Sustainable maintenance | Pinned CI actions, dependency audits, coverage gate, living specs |

## 5. Scope

### In scope

- Protocol core: frames, priorities, skeleton, patches, reconstruction.
- Parsing (SIMD, zero-copy, partial), compression (gzip/zlib, brotli, zstd with dictionaries), schema validation.
- Server adapters (axum HTTP, SSE/NDJSON, WebSocket), client adapters (WebSocket client, `pjs-js-client`, WASM).
- Security controls, observability (metrics), configuration, release and CI pipeline.

### Out of scope

> [!danger]
> - A general-purpose JSON database, query language or GraphQL replacement.
> - Framework-level integration (React Server Components, GraphQL servers).
> - Authentication product features beyond the provided middleware (API key, optional JWT).
> - Stable-Rust support (tracked as a goal, not delivered).
> - A finalized 1.0 wire format (draft).

## 7. Constraints

- Nightly Rust toolchain pinned (GAT zero-cost ports); MSRV declared 1.89.
- Pre-1.0: no backward-compatibility guarantee, breaking changes recorded in CHANGELOG.
- `pjs-domain` must remain WASM-compatible and free of runtime dependencies.
- Distribution: crates.io (`pjson-rs`, `pjson-rs-domain`) and npm (`pjs-wasm` bindings; see [[SRS-pjs-2026-11-15]] for naming drift).

## 8. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Wire format still draft | consumers break between versions | document in CHANGELOG, spec draft, feedback loop |
| Nightly requirement blocks adoption | smaller user base | goal BO-006; track stable GAT availability |
| DoS via parsers/decompressors | security incident | bounded limits, bomb detection, fuzzing, advisories |
| Spec/code drift | wrong decisions | living specs verified against code ([[MOC-specs]]) |
